# Практическая работа: приложение «Посты» (TypeScript + MongoDB + React)

## Цель

Написать бэкенд на Express + Mongoose + TypeScript и подключить к нему фронтенд
на React + TypeScript. Пользователь может посмотреть список постов и добавить новый.

Работа состоит из двух частей. Начинайте с бэкенда: пока нет API, фронтенду
нечего показывать.

---

## Общая модель данных

Это главное в задании: **один и тот же пост описан одинаково на бэке и на фронте.**
Вот объект, который должен приходить с сервера:

```ts
{
  id: '65f1a2b3c4d5e6f7a8b9c0d1',
  title: 'Зачем типизировать пропсы',
  body: 'Чтобы невалидное состояние не компилировалось.',
  createdAt: '2026-08-21T10:15:30.000Z',
}
```

Опишите его интерфейсом. Этот интерфейс нужен и на бэке, и на фронте —
напишите его дважды, в каждом проекте свой файл (общие типы между проектами
мы пока не подключаем):

```ts
export interface Post {
  id: string;
  title: string;
  body: string;
  createdAt: string;
}
```

> **Почему `id` — строка, а не число?**
> MongoDB сама создаёт каждому документу поле `_id`, и это не число, а длинная
> строка вида `65f1a2b3c4d5e6f7a8b9c0d1`. Сделать сквозную нумерацию 1, 2, 3
> в MongoDB можно, но для этого нужна отдельная коллекция-счётчик — это тема
> следующих занятий. Поэтому договариваемся: **`id` у нас строка.**
>
> Заодно это важный навык: бэкенд не отдаёт наружу то, что лежит в базе,
> «как есть». Он приводит данные к тому виду, о котором договорился с фронтом.
> Поле называется `id`, а не `_id`, и никакого `__v` в ответе быть не должно.

# Часть 1. Бэкенд

## Что должно получиться

| Метод  | Маршрут      | Тело запроса        | Ответ            | Статус |
|--------|--------------|---------------------|------------------|--------|
| GET    | `/posts`     | —                   | массив постов    | 200    |
| GET    | `/posts/:id` | —                   | один пост        | 200    |
| POST   | `/posts`     | `{ title, body }`   | созданный пост   | 201    |
| DELETE | `/posts/:id` | —                   | `{ success: true }` | 200 |

Ошибки возвращаем в формате `{ "error": "текст ошибки" }`:

- **400** — пользователь прислал плохие данные (пустой `title`, нет `body`).
- **404** — поста с таким `id` в базе нет.

## Шаг 1. Создайте проект

Соберите проект так же, как мы делали в `balance-app`:

- `npm init -y`
- зависимости: `express`, `mongoose`, `dotenv`, `cors`
- dev-зависимости: `typescript`, `@types/express`, `@types/node`, `@types/cors`, `tsx`
- `tsconfig.json` со `strict: true`, `rootDir: "src"`, `outDir: "dist"`
- в `package.json`: `"type": "module"` и скрипты `dev`, `build`, `start`

Новый пакет здесь только один — **`cors`**. Он нужен, потому что фронтенд будет
работать на другом порту (`5173`), чем бэкенд (`3000`), а браузер по умолчанию
запрещает такие запросы. Подключается одной строкой: `app.use(cors())`.

Не забудьте про `.env` с `MONGO_URI` и `PORT` и про `.gitignore`.

## Шаг 3. Модель — `src/models/Post.ts`

Опишите схему с полями:

- `title` — строка, обязательное поле;
- `body` — строка, обязательное поле;
- `createdAt` — дата создания.

**Подсказка про `createdAt`.** Не заводите это поле руками. Передайте схеме
вторым аргументом настройку `{ timestamps: true }` — mongoose сам добавит
`createdAt` и `updatedAt` и сам их заполнит:

```ts
const postSchema = new Schema({ /* поля */ }, { timestamps: true });
```

## Шаг 4. Функция-конвертер

Из базы приходит документ с `_id`, `__v` и датой в виде объекта `Date`.
Наружу нужен объект по интерфейсу `Post`. Напишите одну маленькую функцию,
которая делает это превращение, и вызывайте её во всех маршрутах:

```ts
function toPost(doc: /* тип документа */): Post {
  return {
    id: doc._id.toString(),
    title: doc.title,
    body: doc.body,
    createdAt: doc.createdAt.toISOString(),
  };
}
```

Так у вас в одном месте описано, как выглядит ответ сервера. Если завтра
добавится новое поле — править нужно будет только здесь.

## Шаг 5. Маршруты — `src/routes/posts.routes.ts`

Требования к каждому маршруту:

**`GET /posts`** — вернуть все посты, новые сверху.
Подсказка: `.sort({ createdAt: -1 })`.

**`GET /posts/:id`** — найти пост по `id`.
Если `findById` вернул `null` — ответить статусом 404 и `{ error: 'Пост не найден' }`.

> **Осторожно.** Если в адресе прислали строку, которая не похожа на настоящий
> `_id` (например, `/posts/abc`), `findById` не вернёт `null`, а **бросит ошибку**.
> Оберните маршрут в `try/catch` и в `catch` отвечайте 404 — этого достаточно.

**`POST /posts`** — создать пост.
Перед созданием проверьте данные и при ошибке верните 400:

- `title` и `body` — это строки;
- после `.trim()` они не пустые;
- `title` не длиннее 100 символов.

Проверку вынесите в отдельную функцию, чтобы маршрут остался коротким.
Сам маршрут при успехе отвечает статусом **201** и объектом созданного поста.

**`DELETE /posts/:id`** — удалить пост.
Если удалять нечего — 404. Подсказка: `findByIdAndDelete` возвращает удалённый
документ или `null`.

## Шаг 6. `server.ts`

Как в `balance-app`, плюс `app.use(cors())`. Не забудьте: `import 'dotenv/config'`
самой первой строкой, `app.use(express.json())` до маршрутов.

## Шаг 7. Проверьте бэкенд до того, как писать фронт

Через Postman или curl:

```bash
curl -X POST http://localhost:3000/posts -H "Content-Type: application/json" -d "{\"title\": \"Первый пост\", \"body\": \"Текст поста\"}"
```

```bash
curl http://localhost:3000/posts
```

Убедитесь, что:

- в ответе есть `id`, и **нет** `_id` и `__v`;
- `createdAt` — строка вида `2026-08-21T10:15:30.000Z`, а не объект;
- пустой `title` даёт 400, а `/posts/abc` даёт 404;
- после перезапуска сервера посты на месте.

# Часть 2. Фронтенд

Создайте проект: `npm create vite@latest posts-frontend -- --template react-ts`

## Шаг 1. Типы и работа с API

Создайте `src/types.ts` с тем же интерфейсом `Post`, что и на бэке.

Создайте `src/api.ts` — все запросы к серверу живут только здесь, в компонентах
никаких `fetch`. Две функции:

```ts
const BASE_URL = 'http://localhost:3000';

export async function getPosts(): Promise<Post[]> {
  // ...
}

export async function createPost(title: string, body: string): Promise<Post> {
  // ...
}
```

Разберитесь, что означает запись `Promise<Post[]>`. Это и есть тот самый
«базовый дженерик»: `Promise` — обещание, а в угловых скобках то, **чем**
это обещание разрешится. Функция `async` всегда возвращает промис, поэтому
писать `Promise<...>` в её типе обязательно.

Внутри функций не забудьте проверить `response.ok` и бросить ошибку с текстом
из ответа сервера, если запрос не удался.

## Шаг 2. Компонент `PostCard`

Отдельный компонент, который показывает один пост: заголовок, текст, дату.

Пропсы типизируйте через `interface`:

```ts
interface PostCardProps {
  post: Post;
}
```

Дату выведите в читаемом виде: `new Date(post.createdAt).toLocaleDateString()`.

## Шаг 3. Список постов в `App.tsx`

Нужны три состояния:

```ts
const [posts, setPosts] = useState<Post[]>([]);
const [isLoading, setIsLoading] = useState<boolean>(true);
const [error, setError] = useState<string | null>(null);
```

Обратите внимание на `useState<Post[]>([])` — это тоже дженерик. Если написать
просто `useState([])`, TypeScript решит, что это массив `never[]`, и не даст
положить туда посты.

`string | null` для ошибки — это **union type**: либо строка с текстом ошибки,
либо `null`, когда ошибки нет.

Загрузите посты в `useEffect` при первом рендере и покажите:

- «Загрузка...», пока `isLoading === true`;
- текст ошибки, если `error !== null`;
- «Постов пока нет», если массив пустой;
- иначе — список `PostCard`.

## Шаг 4. Форма добавления поста

Компонент с двумя полями (`input` для заголовка, `textarea` для текста)
и кнопкой «Добавить».

Требования:

- поля — контролируемые (значение в `useState`, обновление в `onChange`);
- кнопка заблокирована, если хотя бы одно поле пустое или запрос уже идёт;
- при отправке формы обязательно `e.preventDefault()`;
- после успешного создания поля очищаются, а новый пост появляется в списке
  **без перезагрузки страницы**;
- если сервер вернул ошибку — показать её пользователю.

Подумайте, как новый пост попадёт в список. Есть два пути: заново запросить
все посты с сервера или добавить пришедший объект в уже имеющийся массив
(`setPosts([newPost, ...posts])`). Второй вариант быстрее — используйте его.

Типизация обработчика формы:

```ts
async function handleSubmit(e: React.FormEvent<HTMLFormElement>) { }
```

## Что использовать нельзя

Задание проверяет умение работать с базовыми типами. Поэтому:

- **можно:** `interface`, `type`, union (`string | null`), базовые дженерики
  (`Promise<Post[]>`, `useState<Post[]>`), `as` для уточнения типа;
- **нельзя:** `Omit`, `Pick`, `Partial`, `Record`, свои дженерик-функции
  `<T>(...)`, условные типы, `enum`, декораторы;
- **нельзя `any`.** Если хочется написать `any` — значит, тип ещё не продуман.
  Для данных неизвестной формы есть `unknown`.

Также не нужно: авторизации, отдельного слоя сервисов, глобального стора,
роутера, библиотек для запросов. Только то, что перечислено в задании.

## Критерии приёмки

**Бэкенд**

- [ ] Проект собирается: `npm run build` проходит без ошибок TypeScript.
- [ ] Работают все четыре маршрута.
- [ ] Ответ сервера точно соответствует интерфейсу `Post`: есть `id`, нет `_id` и `__v`.
- [ ] `createdAt` — строка ISO.
- [ ] Невалидные данные дают 400, несуществующий пост — 404, оба с полем `error`.
- [ ] Данные сохраняются после перезапуска сервера.
- [ ] Строка подключения лежит в `.env`, а `.env` записан в `.gitignore`.

**Фронтенд**

- [ ] Список постов загружается с сервера, новые сверху.
- [ ] Есть состояния загрузки, ошибки и пустого списка.
- [ ] Форма добавляет пост, и он сразу появляется в списке.
- [ ] Кнопка блокируется на пустых полях и во время запроса.
- [ ] Пропсы компонентов типизированы, `any` в проекте нет.

## Задания со звёздочкой

Беритесь за них, только когда основная часть полностью работает.

1. **Удаление поста.** Кнопка на карточке, вызов `DELETE /posts/:id`,
   удаление из списка на фронте.
2. **Редактирование.** Маршрут `PATCH /posts/:id` на бэке и режим правки
   в карточке на фронте.
3. **Поиск.** Поле ввода на фронте, параметр `?search=` на бэке.
   Подсказка: в MongoDB это `Post.find({ title: { $regex: search, $options: 'i' } })`.
4. **Счётчик символов** под полем «Текст поста» и запрет отправки, если
   текст длиннее 500 символов — одинаково проверенный и на фронте, и на бэке.
