# Техническое задание: бэкенд для блога + авторизация на фронте

Фронтенд с постами уже написан. Задача — поднять для него полноценный сервер:
регистрация, вход, создание постов от имени залогиненного пользователя.

Это ТЗ, а не пошаговая инструкция: что должно получиться — описано точно,
**как** это написать — решаете вы. Подсказки по ключевым местам есть в конце
каждого раздела.

---

## 1. Что должно получиться

Неавторизованный пользователь:

- видит список постов;
- видит формы «Вход» и «Регистрация»;
- **не может** создать пост.

Авторизованный пользователь:

- видит своё имя в шапке и кнопку «Выйти»;
- создаёт посты, автор проставляется автоматически;
- после перезагрузки страницы остаётся залогиненным.

---

## 2. Модель данных

### User

| Поле | Тип | Условия |
| --- | --- | --- |
| `id` | integer | PK, автоинкремент |
| `name` | string | обязательное |
| `email` | string | обязательное, уникальное |
| `password` | string | обязательное, хранится **только в виде хеша** |

### Post

| Поле | Тип | Условия |
| --- | --- | --- |
| `id` | integer | PK, автоинкремент |
| `title` | string | обязательное |
| `subtitle` | string | краткое описание, обязательное |
| `body` | text | обязательное |
| `subject` | string | тема/рубрика |
| `userId` | integer | FK на `users.id` |
| `createdAt` | timestamp | ставится автоматически |

**Про автора.** Отдельного поля `author` в таблице быть не должно — иначе имя
пользователя продублируется и разъедется после смены имени. Автор хранится как
`userId` (связь), а в ответе клиенту отдаётся имя, подтянутое из `users`.

Связь: `User.hasMany(Post)`, `Post.belongsTo(User)`.

Клиенту пост уходит примерно так:

```json
{
  "id": 3,
  "title": "Как работает JWT",
  "subtitle": "Коротко о том, зачем нужен токен",
  "body": "Полный текст поста…",
  "subject": "Backend",
  "author": "Иван",
  "createdAt": "2026-08-25T10:15:30.000Z"
}
```

## 3. API

| Метод | Путь | Тело запроса | Ответ | Доступ |
| --- | --- | --- | --- | --- |
| `POST` | `/api/auth/register` | `{ name, email, password }` | `201` + `{ token, user }` | всем |
| `POST` | `/api/auth/login` | `{ email, password }` | `200` + `{ token, user }` | всем |
| `GET` | `/api/posts` | — | `200` + массив постов | всем |
| `GET` | `/api/posts/:id` | — | `200` + пост | всем |
| `POST` | `/api/posts` | `{ title, subtitle, body, subject }` | `201` + созданный пост | только с токеном |
| `DELETE` | `/api/posts/:id` | — | `204` | только автор поста |

`user` в ответах авторизации — это `{ id, name, email }`. **Пароль (даже хеш) в
ответ попадать не должен никогда.**

### Коды ошибок

| Ситуация | Код | Тело |
| --- | --- | --- |
| не заполнены обязательные поля | `400` | `{ message: '...' }` |
| email уже занят | `409` | `{ message: 'Email already in use' }` |
| неверный email или пароль | `401` | `{ message: 'Invalid email or password' }` |
| нет токена / токен протух | `401` | `{ message: 'No token provided' }` |
| пытается удалить чужой пост | `403` | `{ message: 'Forbidden' }` |
| поста нет | `404` | `{ message: 'Post not found' }` |

Важное правило безопасности: при неудачном входе ответ **одинаковый** и для
несуществующего email, и для неверного пароля. Иначе по разнице ответов можно
перебрать, какие адреса зарегистрированы.

## 4. Бэкенд: что делать

Стек: Express + Sequelize + PostgreSQL (или MySQL), `bcrypt`, `jsonwebtoken`,
`cors`, `dotenv`.

### 4.1. Структура

```
src/
  db/
    connection.js
    models/          User.js, Post.js, index.js (связи)
    migrations/
  middleware/
    authenticate.js
  routes/
    auth.js
    posts.js
  server.js
.env
```

### 4.2. Регистрация

Порядок действий: проверить, что поля пришли → проверить, что email свободен →
захешировать пароль → создать пользователя → выдать токен.

Подсказки:

- пароль хешируется через `bcrypt.hash(password, 10)`. **Никогда** не сохраняйте
  пароль как есть, даже «на время разработки»;
- хеширование удобно повесить на хук модели `beforeCreate` — тогда роут не
  сможет об этом забыть;
- проверку `email` не делайте вручную поиском по базе, если стоит
  `unique: true` — ловите ошибку `SequelizeUniqueConstraintError` и отвечайте
  `409`.

### 4.3. Вход

Найти пользователя по email → сравнить пароль → выдать токен.

Подсказки:

- сравнение только через `bcrypt.compare(введённый, хеш)`. Обычное `===` не
  сработает: хеш каждый раз разный;
- метод `comparePassword` удобно объявить прямо на модели — как у вас в примере
  с занятия;
- в payload токена кладите **минимум**: `{ id: user.id }`. Токен не шифруется, а
  только подписывается — его содержимое любой может прочитать на jwt.io. Пароль,
  email и роли туда класть не надо.

### 4.4. Middleware `authenticate`

Достаёт токен из заголовка `Authorization: Bearer <token>`, проверяет подпись,
кладёт id пользователя в `req` и передаёт управление дальше.

Подсказки:

- имя свойства на `req` (`req.userId`) вы придумываете сами — важно лишь
  использовать его одинаково во всех роутах. А вот `payload.id` обязано
  совпадать с тем, что вы положили в `jwt.sign()`;
- `jwt.verify` бросает исключение — оборачивайте в `try/catch` и отвечайте
  `401`, а не роняйте сервер;
- middleware вешается только на защищённые роуты:
  `router.post('/', authenticate, handler)`.

### 4.5. Посты

- `GET /api/posts` — отдаёт список **с именем автора**. В Sequelize это
  `include` с моделью `User` и `attributes: ['name']`. Не делайте отдельный
  запрос за автором внутри цикла — это классическая проблема N+1;
- сортировка — новые сверху (`order: [['createdAt', 'DESC']]`);
- `POST /api/posts` — `userId` берётся **только** из `req.userId`. Если брать
  его из тела запроса, любой сможет опубликовать пост от чужого имени. Это
  главная мысль всего задания;
- `DELETE /api/posts/:id` — сначала найти пост, потом сравнить `post.userId` с
  `req.userId`. Не совпало → `403`.

### 4.6. Мелочи, на которых обычно застревают

- `app.use(express.json())` — без него `req.body` будет `undefined`;
- `cors` — фронт на `5173`, бэк на `3000`, это разные origin. Без `cors()`
  браузер заблокирует запросы;
- `.env` (`JWT_SECRET`, параметры БД) **обязательно** в `.gitignore`;
- секрет — длинная случайная строка, а не `secret123`;
- срок жизни токена задаётся третьим аргументом `jwt.sign`: `{ expiresIn: '1d' }`.

## 5. Фронтенд: что делать

### 5.1. Типы

Опишите то, что приходит с сервера, — по одному типу на сущность:

```ts
interface User { id: number; name: string; email: string }
interface Post { id: number; title: string; subtitle: string; body: string;
                 subject: string; author: string; createdAt: string }
interface AuthResponse { token: string; user: User }
```

Помните: сервер присылает `unknown` — TypeScript вам верит на слово. Аннотация
`await res.json() as Post[]` не проверяет данные, а только описывает ваши
ожидания. Если поле переименуется на бэке, компилятор промолчит, а приложение
сломается в рантайме.

### 5.2. Слой запросов

Заведите один файл `api.ts` и держите все `fetch` там. Компоненты не должны
знать про URL, заголовки и токены.

Подсказки:

- базовый URL — в константу (потом переедет в `.env`);
- одна функция-обёртка, которая сама подставляет
  `Authorization: Bearer ${token}` и `Content-Type: application/json`;
- `fetch` **не бросает исключение** на 400/401/500 — проверяйте `res.ok`
  вручную и кидайте ошибку сами. Это ошибка №1 у всех, кто пришёл с `axios`.

### 5.3. Хранение авторизации

Что нужно хранить: `token` и `user`.

- в состоянии React — чтобы интерфейс перерисовывался;
- в `localStorage` — чтобы вход переживал перезагрузку страницы.

Подсказки:

- начальное состояние читайте из `localStorage` в инициализаторе `useState`;
- выход — это `setUser(null)` + очистка `localStorage`;
- если токен протух, сервер ответит `401` — обработайте это как автоматический
  выход, иначе пользователь будет тыкать в кнопки, а ничего не будет происходить;
- `localStorage` виден любому скрипту на странице. Для учебного проекта это
  нормально, но знайте: в продакшене токены чаще кладут в httpOnly-cookie.

### 5.4. Формы входа и регистрации

Требования:

- регистрация: имя, email, пароль; вход: email, пароль;
- кнопка заблокирована, пока идёт запрос — иначе двойной клик создаст двух
  пользователей;
- ошибка с сервера показывается **в форме**, а не в `alert` и не только в
  консоли;
- после успеха — форма закрывается, в шапке появляется имя.

Подсказки:

- переиспользуйте свои `Input` и `Button` — это ровно тот случай, ради которого
  писался UI-кит;
- пароль — это `<input type="password">`;
- состояние запроса удобно описать одним значением, а не тремя флагами:
  `'idle' | 'loading' | 'error'`. Так невозможно получить «одновременно
  загружается и ошибка».

### 5.5. Форма создания поста

- показывается **только** залогиненному пользователю (условный рендеринг);
- поля: `title`, `subtitle`, `body`, `subject`. Поля «автор» в форме нет —
  автор берётся из токена на сервере;
- после успешного создания пост появляется в списке без перезагрузки страницы.

Подсказки:

- проще всего — добавить созданный пост (его вернул сервер) в начало массива в
  состоянии;
- прятать форму от гостя — вопрос удобства, а не безопасности: настоящая защита
  живёт на сервере. Спрятанная кнопка не мешает отправить запрос руками.

## 6. Порядок работы

1. Модели и миграции, проверить, что таблицы создались.
2. Регистрация и вход — **проверять в Postman/Thunder Client**, до фронта.
   Убедиться, что в базе лежит хеш, а не пароль.
3. `authenticate` + защищённое создание поста. Проверить, что без токена
   приходит `401`.
4. `GET /api/posts` с именем автора.
5. Только теперь — фронт: `api.ts`, формы, хранение токена.
6. Удаление поста и проверка прав (`403` на чужой).

Почему так: если начать с фронта, вы будете отлаживать сразу два незнакомых
слоя и не поймёте, на чьей стороне ошибка.

---

## 7. Критерии приёмки

**Бэкенд**

- [ ] в базе лежит хеш пароля, а не пароль;
- [ ] пароль не возвращается ни в одном ответе;
- [ ] `POST /api/posts` без токена → `401`;
- [ ] `userId` берётся из токена, а не из тела запроса;
- [ ] удаление чужого поста → `403`;
- [ ] в списке постов есть имя автора, и оно приходит одним запросом (без N+1);
- [ ] при неверном email и неверном пароле ответ одинаковый;
- [ ] `.env` не в репозитории.

**Фронтенд**

- [ ] все `fetch` в одном модуле, компоненты про URL не знают;
- [ ] ответы сервера описаны типами, `any` нет;
- [ ] ошибки сервера видны пользователю в интерфейсе;
- [ ] кнопка отправки блокируется на время запроса;
- [ ] после перезагрузки страницы пользователь остаётся залогиненным;
- [ ] форма создания поста не показывается гостю;
- [ ] новый пост появляется в списке без перезагрузки.

## 8. Со звёздочкой

1. **Редактирование поста** — `PATCH /api/posts/:id`, только для автора.
2. **Пагинация** — `GET /api/posts?page=1&limit=10`, ответ вида
   `{ items, total }`.
3. **Фильтр по теме** — `GET /api/posts?subject=Backend`.
4. **Валидация на сервере** через `zod`: одна схема — и проверка тела запроса,
   и понятное сообщение об ошибке.
5. **Refresh-токен**: короткоживущий access (15 минут) + долгоживущий refresh в
   httpOnly-cookie. Это уже взрослая тема — беритесь, если основное готово.
